# TODO 03 — Helpers & Runtime Validation

**Source of truth:** `docs/mfe-events-project-brief.md` (and this TODO)  
**Goal of this TODO only:** Add **thin typed helpers** around `CustomEvent` / `window`, plus **runtime validation** of payloads (`schemaVersion` required and valid; shape checks via `class-validator` / `class-transformer` where appropriate). No USAGE.md yet. No event-bus, RxJS, or Angular services.

## Constraints

- Helpers stay **minimal**. Pure functions that create, narrow, or dispatch `CustomEvent`s.
- `schemaVersion` is **required** on every payload. Creating an event without it (or with a mismatched major) must fail at runtime in the create/dispatch path.
- Validation should be practical, not bureaucratic: required fields, enums/unions, basic types. Do not over-validate `initialData` beyond “plain object if present”.
- Prefer dependencies already common in the ecosystem: `class-validator` + `class-transformer`. Add them as **dependencies** (or peerDependencies if that matches sibling packages — prefer normal dependencies so validation works out of the box for consumers of the helpers).
- Reflect-metadata: if class-validator decorators need it, document that consumers who call validated helpers must import `reflect-metadata` once at app entry (or ensure the lib side handles what it can without forcing a global side effect in the package entry). Avoid surprising global side effects in the public entry if possible.
- All new public APIs need JSDoc (inputs, throws, who should call them).

### 2. Validation model [DONE]

Choose one clear approach and stick to it:

**Recommended approach**

- Keep **interfaces** as the public payload types (from TODO 02).
- Add internal (or exported) **DTO classes** with `class-validator` decorators, one per payload (or a shared base for `ModuleIdentity` + `schemaVersion`).
- Provide a small internal `validatePayload(type, detail)` that:
  1. Ensures `detail` is a non-null object
  2. Ensures `schemaVersion` is present and equals `SCHEMA_VERSION` (or is in an allowed set if you explicitly support more than one)
  3. Runs `class-validator` on the matching DTO (via `plainToInstance` + `validateSync` or async equivalent)
  4. Throws a dedicated error type on failure (see task 3)

- [x] Implement DTO classes mirroring each payload interface (required vs optional fields must match the interfaces).
- [x] Shared fields (`moduleType`, `instanceId`, `schemaVersion`) can live on a base class to avoid duplication.
- [x] `ShowNotificationPayload` and `ThemeChangedPayload` DTOs omit module identity fields.
- [x] Do **not** change the public interfaces to classes unless there is a strong reason; prefer interfaces + DTO validation behind the helpers.

Alternative (only if DTOs become too heavy): a hand-written validator per payload without class-validator. Prefer class-validator since it was explicitly requested.

### 4. Core helpers (`src/helpers.ts`) [DONE]

Implement and export:

```ts
createMfeEvent<K extends keyof MfeEventMap>(
  type: K,
  detail: MfeEventMap[K]
): CustomEvent<MfeEventMap[K]>;

createShellEvent<K extends keyof ShellEventMap>(
  type: K,
  detail: ShellEventMap[K]
): CustomEvent<ShellEventMap[K]>;

isMfeEvent<K extends keyof MfeEventMap>(
  event: Event,
  type: K
): event is CustomEvent<MfeEventMap[K]>;

isShellEvent<K extends keyof ShellEventMap>(
  event: Event,
  type: K
): event is CustomEvent<ShellEventMap[K]>;
```

Requirements:

- [x] `createMfeEvent` / `createShellEvent`:
  - Validate `detail` before constructing the `CustomEvent`
  - On validation failure → throw `MfeEventValidationError` (do not dispatch invalid data)
  - Use `new CustomEvent(type, { detail, bubbles: true })` unless the brief/repo standard says otherwise; document `bubbles` choice in JSDoc (recommend `bubbles: true` so Shell can listen on `window` or a parent if needed)
- [x] `isMfeEvent` / `isShellEvent`:
  - Type guards only: check `event instanceof CustomEvent` (or equivalent) and `event.type === type`
  - Do **not** re-validate the entire payload in the type guard (keep guards cheap for use in listeners). Optional: shallow check that `detail` is an object.
- [x] JSDoc examples on each helper (minimal, copy-paste friendly).
